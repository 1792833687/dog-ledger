## 1. 背景

两位合伙人准备开始一门生意：**在本地收购小狗，再卖出去。** 目前处于**开张前筹备期（0 单）**。

> ⚠️ **原定链路已不可用。** 最初设想是"通过抖音引流（短视频/评论区/私信）→ 加微信 → 微信成交"。合规调研查明：抖音**明文禁止**站外导流（含微信号、二维码及各类变体），处罚上限为永久封禁账号；而「宠物活体 / 狗活体」类目在抖音电商**暂停招商**。详见 §7.1、§9 与 `docs/compliance/2026-10-02-犬只交易合规要点-平台篇.md`。**销售渠道是一个尚未解决的商业决策。**

合伙模式：**共同出资、共担风险、利润分成。**

用户在需求澄清阶段勾选了全部五个痛点维度（账目分钱、客户跟进、犬只台账、内容归因、售后口碑）。经讨论确认：**这五个维度是同一条业务流水线（收狗 → 医疗 → 拍摄 → 发布 → 咨询 → 成交 → 售后）的五个视角，不可能在第一版全部做好。**

### 1.1 核心矛盾

一笔生意都还没做，因此任何"记录 + 分析"工具都是空的。但**分钱规则、成本结构、损耗摊薄恰恰在开张前最该算清楚**——等 10 只狗卖完才发现分错，为时已晚。

因此第一版的定位不是"账本"，而是**决策台**：

> 先把会算错的账算对，再把会忘的事记住。

### 1.2 第一版要解决的唯一问题

**在出门看狗之前，知道自己最多能出多少钱，以及低于什么价格绝对不能卖。**

### 1.3 非目标（第一版明确不做）

| 不做的事 | 原因 |
|---|---|
| 客户线索跟进 / CRM | 0 单阶段没有线索可录，界面会空转 |
| 抖音内容与流量归因 | 抖音不开放私信/评论数据接口，无法自动归因；现在没有内容；**且这条引流链路本身合规性待定（见 7.1）** |
| 售后包赔 / 退货管理 | 尚未发生；等真实发生后再按真实流程设计 |
| 多人实时同步 | 用户选择"一人记账"，不需要服务器 |
| 微信小程序 | 用户选择"不卡形式，好用优先"；小程序需主体资质与审核，对内部工具是纯负担 |
| 库存出栏周期分析 | 缺少数据，且与核心目标无关 |

## 2. 关键决策与理由

| # | 决策 | 理由 |
|---|---|---|
| **D1** | 交付形态为**纯前端 PWA**（手机浏览器打开 + 加到桌面），不是微信小程序 | 这是内部记账工具，不是给客户看的。小程序正式发布需企业/个体户主体（认证费 300/年）与审核周期；PWA 零资质、零审核、当天可用。将来若要小程序，只需再包一层壳。 |
| **D2** | 数据存**本机 IndexedDB**，无后端、无账号、无月费 | 用户明确选择"我一个人记账就行，伙伴偶尔看结果"。换来零成本零维护。**代价是数据只存在一台设备上，必须靠手动备份保证安全**（见第 7 节，这是本项目最大的风险）。 |
| **D3** | 第一版范围 = **保本决策台 + 犬只批次台账 + 资金流水 + 分账报表** | 这是唯一在 0 单阶段立即有价值的组合。软件的价值来自数据密度，不是功能数量。 |
| **D4** | **批次**是损耗摊薄的计算单位，不是单只狗 | 死亡、运输、疫苗都是"一趟一批"发生的。死亡的个体是谁不重要，重要的是这批死了几只、活了几只、损失摊给谁。平铺成单表则无法表达。 |
| **D5** | **垫付 ≠ 出资**，两者必须分开记 | 合伙最常见的错账。A 出门收狗先垫 5000 现金是垫付（要从池子报销还给 A）；A 往池子打 5000 入伙是出资（本金）。混记则三个月后无法算清。 |
| **D6** | 所有金额计算写成**纯函数**，存储层做薄接口封装 | 为将来"两人实时共享"留口：届时只需把存储层从本地换成云端，界面与算法一行不改。 |
| **D7** | **流水（LedgerEntry）是唯一的真相来源**，狗与批次只是分类维度 | 避免"狗的售价存在狗表、同时在流水里又记一笔收入"这类双写不一致。售价由关联到该狗的收入流水推导。 |
| **D8** | 录入必须"**3 秒原则**" | 用户已经指出：录一条要 30 秒，两天后就不会再录。所有录入路径都要先想清楚最少字段。 |
| **D9** | **检疫与病死犬无害化处理进成本模型**，作为两个独立的内置成本项 | 合规调研（`docs/compliance/`）查证：检疫是出售的**法定前置**，不是可选的合规开销；病死犬无害化处理是强制支出。这两笔钱是真金白银的现金流出，把它们排除在外的"保本价"是错的。**它们与"损耗摊薄"必须分开理解**：摊薄是账面重分配（一分钱没多花），检疫与处理是真支出（钱出去了）。 |
| **D10** | **不替用户做商业决策，但把合规事实摆到明面上** | 抖音明文禁止站外导流、狗活体类目暂停招商——这两件事都不是写软件能解决的。软件能做的：把合规成本算进保本价，并把"引流链路待定"写进文档，避免第二期给一条不存在的路修路标。改动已批准的设计须先经用户同意（本次已获批准）。 |
| **D11** | **批次必须记「计划去向」，并能按渠道分别算保本价** | 线下成交是唯一走得通的路径（见 7.1），而各渠道成本结构差别极大：卖断给宠物店几乎无额外成本，自零售要承担退狗与售后，犬市要摊场地费与往返油费，平台电商要包装 + 有轨迹物流 + 死亡赔付。如果只有一个笼统的"批次成本"，用户无法回答"这批走哪条路更划算"。**渠道清单刻意不含任何抖音选项**——那两条路已被查证堵死，留在选项里等于诱导。 |
| **D12** | **检疫流程台账提前到第一期** | 检疫是每一单出售的法定前置；一证多用（数量超出载明部分、种类不符、使用转让的证明）按"未经检疫"处理，落进货值 15~30 倍那一档，负责人 5 年禁业。**没有地方记录证明编号与有效期，就只能靠脑子记——这正是最贵的那类遗忘。** 原计划把它放第二期，前提是"货源可能转为与繁育基地签约"；现在前提变了：无论走哪条渠道都必须有证明，所以它是第一期的关键路径，不是可选功能。 |

## 3. 领域模型

### 3.1 三个层次

```
池子（钱从哪来）
  └── 批次（一次收回来的货）
        └── 单只狗（独立成本、状态、成交）
```

### 3.2 实体定义

```ts
// ---- 设置 ----
type Settings = {
  partners: { id: string; name: string; shareRatio: number }[]  // shareRatio 之和为 1
  costItems: CostItemDef[]        // 可配置成本项
  targetMarginRate: number        // 目标毛利率，用于建议售价，默认 0.3
  expectedMortalityRate: number   // 预估死亡率默认值，用于决策台，默认 0.15
}

type CostItemDef = {
  id: string
  name: string                    // 如"收购价""运输+笼具""疫苗驱虫医疗"
  scope: 'batch' | 'dog'          // 这笔钱发生在批次层面还是单只狗层面
  isBuiltin: boolean              // 内置项不可删除，只能改名
}

// ---- 批次 ----
type Batch = {
  id: string
  name: string                    // 如"10月3日 李村一批"
  date: string                    // ISO 日期
  source: string                  // 货源：农户 / 养殖场 / 同行 / 其他
  note: string
  status: 'active' | 'closed'     // closed 后不再计入"在库"
}

// ---- 单只狗 ----
type Dog = {
  id: string
  batchId: string
  code: string                    // 编号，如 "1003-1"
  breed: string
  sex: 'male' | 'female' | 'unknown'
  ageMonths: number | null
  status: 'in_stock' | 'sold' | 'dead' | 'returned'
  photoRef: string | null         // 可选，存缩略图
  note: string
}

// ---- 资金流水（唯一真相来源）----
type LedgerEntry = {
  id: string
  date: string
  type: 'injection' | 'expense' | 'income' | 'reimbursement' | 'distribution'
  category: string                // expense 关联 CostItemDef.id；income/distribution 用固定值
  amount: number                  // 恒为正数，方向由 type 决定
  paidBy: 'pool' | string         // expense 专用：池子直付 或 某合伙人垫付
  payee: string | null            // reimbursement / distribution 专用：收款人 partnerId
  batchId: string | null
  dogId: string | null
  note: string
}
```

### 3.3 五种流水对四本账的影响

项目维护四本账：**池子现金（cash）**、**垫付账（advance）**、**注资本金（capital）**、**分红账（distributed）**，外加一套**损益**统计。

| 类型 | 池子现金 | 垫付账 | 注资本金 | 分红账 | 损益 |
|---|---|---|---|---|---|
| `injection` 注资 | +amount | — | 注资人 +amount | — | — |
| `expense` 支出（池子直付） | −amount | — | — | — | 成本 +amount |
| `expense` 支出（某人垫付） | 不变 | 垫付人 +amount | — | — | 成本 +amount |
| `income` 收入 | +amount | — | — | — | 收入 +amount |
| `reimbursement` 报销 | −amount | 收款人 −amount | — | — | — |
| `distribution` 分红 | −amount | — | — | 收款人 +amount | — |

**关键设计：分红是可选的。** 如果两人决定把利润留在池子里继续周转，就**不记** `distribution`。报表仍然显示"应分未分权益"，钱留在池子里当本金。这避免了"必须先把钱拿出来再打回去"的荒谬流程。

### 3.4 计算规则（全部为纯函数）

> 约定：单只狗层面的支出（收购价、疫苗）在一笔流水上**同时写入 `batchId` 与 `dogId`**。因此它既计入批次总成本，也能被单独取出。这是 3.3 "流水是唯一真相来源" 的落地方式。

```ts
// ---- 基础取数 ----
dogOwnCost(dogId)         = Σ expense(dogId = d).amount
batchTotalCost(batchId)   = Σ expense(batchId = b).amount   // 含批次层面与单只狗层面
batchIncome(batchId)      = Σ income(batchId = b).amount
inStockCount(batchId)     = count(status = 'in_stock' | 'returned')   // 退狗回到在库（见 3.4 边界规则）
aliveCount(batchId)       = count(status ≠ 'dead')          // sold 与 returned 都算活着
deadLoss(batchId)         = Σ dogOwnCost(d) for d.status = 'dead'

// ---- ★ 指标 A：批次剩余保本单价（决策用）----
// 回答："剩下的每只至少卖多少钱，整批才不亏"
remainingFloorPrice(batchId) = max(0, batchTotalCost − batchIncome) / inStockCount
// inStockCount = 0 时不显示；结果 = 0 时显示"已回本，剩下的都是利润"

// ---- ★ 指标 B：单只狗摊薄成本（复盘用）----
// 回答："这只狗算上死掉的同伴，真实花了多少钱"
// 摊的是【整批的钱】÷【还活着的只数】，含运输、病死犬处理这类批次层面的支出。
// 不能写成 dogOwnCost + deadLoss/alive：那个式子漏掉批次层面的钱，
// 会让 3.6 案例算出 906.67 而不是 973.33，"真实成本"就名不副实了。
dilutedCost(dogId) = batchTotalCost(batchId) / aliveCount(batchId)
                     // aliveCount = 0（整批死光）时退化为 dogOwnCost(dogId)，不得除零
dogProfit(dogId)   = income(关联到该狗的收入之和) − dilutedCost(dogId)

// ---- 资金三账 ----
poolBalance(entries)        = Σ injection + Σ income − Σ expense(paidBy = 'pool') − Σ reimbursement − Σ distribution
advanceBalance(partnerId)   = Σ expense(paidBy = partnerId) − Σ reimbursement(payee = partnerId)
contributedCapital(partnerId) = Σ injection(partnerId)
distributedTo(partnerId)    = Σ distribution(payee = partnerId)

// ---- 损益与分账 ----
netProfit(from, to)   = Σ income − Σ expense
claimable(partnerId)  = (netProfit 累计 × shareRatio(partnerId)) − distributedTo(partnerId)
```

**为什么需要两个指标（A 和 B）？**
它们回答的是两个不同的问题，不可互相替代：

- **A 面向未来的现金流**："我还差多少回本，剩下的狗必须卖多少钱。" 它随成交实时下降，可归零，极其实用。
- **B 面向过去的经济学**："这批到底赚没赚。" 它把死狗的成本摊到每只活着的狗头上。

用 A 去复盘，已售狗的盈亏会随后来的死亡而变动，越看越乱；用 B 去决策，最后一个买家就要独自承担全部损耗，报价会高得卖不出去。**界面上必须把两者的场景标注清楚。**

### 3.5 决策台模拟公式（还没有批次时使用）

| 输入 | 符号 |
|---|---|
| 预计收到几只 | `n` |
| 每只收购价 | `p` |
| 这趟油费 + 笼具 | `f` |
| 每只疫苗医疗 | `v` |
| **每只检疫费**（抗体检测 + 申报跑腿） | `q` |
| **每只病死犬处理费** | `d`（默认取 `settings.disposalPerDog`） |
| 预估死亡率 | `m`（默认取 `settings.expectedMortalityRate`） |
| 打算卖多少钱 | `s` |

```
预估存活数   = n × (1 − m)
预估死亡数   = n × m
预估总成本   = n × p + f + n × v + n × q + (n × m) × d
                 ↑ 检疫费按【买回来的全部只数】交：狗死了检疫的钱也不退
                                        ↑ 处理费只对【预估死亡】的那部分发生
预估摊薄成本 = 预估总成本 ÷ 预估存活数        ← ★ 这就是保本价
建议售价     = 预估摊薄成本 × (1 + targetMarginRate)
风险模拟(k)  = 若只卖掉 k 只 → 亏损 = 预估总成本 − k × s；每人承担 = 亏损 ÷ 2
```

> ⚠️ **`q` 与 `d` 默认值都是 0，代表"还不知道"，不要当成"不用花钱"。**
> 填 0 时算出的保本价是**偏低**的。这两个数字必须由用户向当地动物卫生监督机构问清后在「设置」里填一次。
> 软件不能编一个看起来合理的数字——那会让人以为算过了。

**边界规则（必须有测试覆盖）：**
- `aliveCount === 0`（整批死光）→ `dilutedCost` 退化为 `dogOwnCost`，除零不得崩溃，界面显示"全损"警告
- `inStockCount === 0`（全部售出）→ 不显示指标 A，只显示指标 B 的最终复盘
- 批次未结束时 `deadLoss` 与 `batchIncome` 都在变，说明**已售出狗的盈亏是浮动的**，界面必须显式标注"按当前损耗率估算"
- `returned`（退狗）的记账方式：狗回到在库（计入 `inStockCount` 与 `aliveCount`），**已发生的医疗成本不冲销**，同时记一笔 `expense`（类别"售后退款"，金额 = 退回给客户的款）关联到该狗。若狗没要回来，则状态保持 `sold`，只记退款支出。
- **退回的狗后来又死了 → 那笔退款不冲销。** 这时账上会同时有三笔：`income/售出`(P)、`expense/售后退款`(P)、以及计入 `deadLoss` 的购置成本 C 与已发生医疗成本 M。这是**对的**：P 与 P 相互抵消，真实亏损 = −(C+M)。若再去冲销退款，P 会被当成净收入留下，账面凭空多出一笔 P 的假利润——比不冲销错得更厉害。批次净利按 `income − totalCost` 算（`src/domain/costing.ts:107`），`deadLoss` 只是展示与摊薄的输入，**不参与净利计算**，不会二次扣除。
- **第一期已知限制：退款记下后没有撤销或改正入口。** `aftercare_refund` 只增不减，金额填错时界面上只能看到「已记退款」。流水纠错（撤销 / 冲销 / 编辑历史流水）**不在第一期范围内**。另外 `src/ui/dogLedger.ts` 的 `refundedCurrentSale` 依赖 `entries` 的**追加顺序**（用数组下标而非 `date` 比先后），将来若引入"编辑 / 删除历史流水"，这两个函数必须同步改。
- 分红比例之和 ≠ 1：保存设置时校验并拒绝

### 3.6 关键案例（用于验证算法与用户沟通）

收购 8 只 × 600 = 4,800；运输 + 笼具 400；疫苗驱虫医疗 8 × 80 = 640；批次总成本 **5,840**。

死亡 2 只，存活 6 只 → 每只存活狗真实成本 = 5,840 ÷ 6 = **973**。

若按收购价思维以 900 卖出，**每只亏 73**，而当事人会以为赚了 300。这是本项目存在的核心理由。

**再加上合规成本（用占位假设：检疫 50 元/只、病死犬无害化处理 200 元/只）：**

检疫 8 × 50 = 400（按买回来的全部 8 只交，死的那 2 只的检疫钱不退）；病死犬处理 2 × 200 = 400。

批次总成本 **5,840 + 800 = 6,640**，存活 6 只 → 每只存活狗真实成本 = 6,640 ÷ 6 ≈ **1,106.67**。

| | 不含合规成本 | 含合规成本 | 差 |
|---|---|---|---|
| 每只存活狗成本 | 973.00 | 1,106.67 | +133.67（**+13.7%**） |
| 以 900 卖出，每只 | 亏 73 | **亏 206.67** | — |

> ⚠️ 上面的 50 元 / 200 元**只是占位假设，不是查到的价格**，仅用于说明量级。
> 真实数字必须由用户向当地动物卫生监督机构问清后填进「设置」——软件不替用户编价格。

### 3.7 检疫台账（合规关键路径）

检疫证明是**每一单出售的法定前置**，不是可选步骤。这一节的规则决定「狗」页面能不能在出事之前把人拦住。

**每只狗要记的 6 个字段**（`Dog` 接口，见 3.2）：

| 字段 | 含义 | 为什么要有 |
|---|---|---|
| `rabiesVaccinatedOn` | 狂犬病疫苗接种日期 | 疫苗是申报检疫的前置，也是"最早可送检日"的起点 |
| `antibodyTestedOn` | 免疫抗体检测日期 | 犬比猫多这一道；没有报告原件不予受理 |
| `antibodyReportNo` | 抗体检测报告编号 | 报告原件会丢，编号不会 |
| `quarantineCertNo` | 《动物检疫合格证明》编号 | **一证多用要按货值 15~30 倍罚**，编号是唯一能自证"哪只狗配哪张证"的东西 |
| `quarantineCertIssuedOn` | 证明签发日期 | 用于计算有效期 |
| `quarantineCertValidUntil` | 证明有效期至 | **过期即不可出售**，必须能在列表上直接看到 |

**两个时间参数做成设置项，不写死在代码里**（`Settings`）：

- `rabiesWaitDays`（默认 21）—— 免疫后需等待的天数。⚠️ **这个 21 不是法定天数**：2026-10-02 取到《犬产地检疫规程》与《狂犬病防治技术规范》两份官方原文后复核，**两份文件里都没有「21 天」**（规程只说「在有效保护期内」，技术规范只说「每年加强免疫一次」）。它更可能是抗体检测的实验室采样窗口要求。做成可配置就是为了让你问清之后改，而不是让软件替你猜。详见 `docs/compliance/2026-10-02-犬只交易合规要点-法规篇.md` §2.9。
- `quarantineLeadDays`（默认 3）—— 申报检疫需提前的天数，《动物检疫管理办法》第八条第二款。

**每只狗由这 6 个字段推导出一个阶段**（纯函数，`domain/quarantine.ts`）：

| 阶段 | 判定 | 下一步该做什么 |
|---|---|---|
| `unvaccinated` | `rabiesVaccinatedOn === null` | 去打狂犬疫苗 |
| `waiting_antibody` | 已接种，但距接种不足 `rabiesWaitDays` 天 | 等（显示还要等几天） |
| `ready_to_test` | 已接种且已满 `rabiesWaitDays` 天，`antibodyTestedOn === null` | 去采血做抗体检测 |
| `waiting_cert` | 已有抗体检测记录，但没有检疫证明 | 准备申报（提前 `quarantineLeadDays` 天） |
| `certified` | `quarantineCertNo` 非空 且 `quarantineCertValidUntil` ≥ 今天 | 可以出售 |
| `cert_expired` | 有证明编号但有效期已过 | **必须重新申报**，不能靠旧证出售 |

**一条铁律**：`isSellable(dog, today)` 只有在 `certified` 阶段才返回 `true`。批次出栏前的检查清单（`preSaleChecklist(data, batchId, today)`）要能把"这批 8 只里有 3 只没有有效检疫证明"直接摆出来——**这是本工具唯一能防止 5 万级罚款的地方。**

> ⚠️ 本节的日期与天数是**提示**，不是法律意见。真正的准绳是当地动物卫生监督机构的答复（见 10.1）。

### 3.8 渠道对照（同一批狗，不同渠道不同保本价）

销售环节已确认只可能发生在线下（见 7.1），而**各渠道的成本结构差别极大**：卖断给宠物店几乎无额外成本；自零售要承担退狗与售后；犬市要摊场地费与往返油费；平台电商要包装、有轨迹物流与死亡赔付。

因此：

- `Batch` 新增 **`plannedChannel: ChannelId`**（默认 `'undecided'`），记录这批狗打算走哪条路。
- `SALES_CHANNELS` 常量列出 9 条渠道（含"未定"），**渠道清单里刻意不含任何抖音选项**——留着会诱导人去走那条会被永久封号的路。每条渠道带一句 `note` 说明其特有成本或风险。
- 决策台新增**渠道对照**：对若干候选渠道分别输入"预期单价 / 每只额外成本 / 该渠道专属固定成本"，输出每个渠道的**每只利润**与**可接受的最低单价（保本单价）**，并标出哪个渠道在给定价格下是亏的。

**渠道对照与 3.5 的决策台共用同一套成本模型**：先算出"每只存活狗的真实成本"（含检疫，见 3.5），再叠加各渠道的额外成本，最后对比单价。**不允许出现"渠道单独一套算法"**——那正是算错钱的地方。

## 4. 界面设计

手机优先，底部**五个**标签页。

| 标签 | 何时使用 | 内容 |
|---|---|---|
| **算** | 出门看狗之前（最高频） | 输入：收几只 / 每只收购价 / 油费笼具 / 疫苗单价 / 每只检疫费 / 每只病死犬处理费 / 预估死亡率 / 打算卖多少。输出：真实成本、**保本价（低于这个价别卖）**、建议售价、风险模拟（只卖掉 60% / 80% / 100% 时两人各亏多少）。另有**渠道对照**（见 3.8）：同一批狗走不同渠道时各自的最低可卖价。可一键"存为批次"直接开始记账（含计划去向）。 |

| **钱** | 每次花钱、收钱时 | 池子现金余额大字 + 快捷记账（+支出 / +收入 / +注资）+ 资金流水列表 + 每人垫付未还额。 |
| **报** | 要分钱、要发对账单时 | 分账结算（净利、每人应得、每人垫付、池子余额）、**一键生成对账单图片**、批次盈亏排行榜、成本结构、死亡率趋势、数据备份导出/导入。 |

### 4.1 给伙伴看账（信任设计）

因为只有一人记账，而两人共同出资，工具必须让"信任有据可依"：

- **一键生成对账单图片**：一张竖版长图，写明本期收了几只、死了几只、花了多少、卖了多少、池子剩多少、每人各分多少。直接发微信，无需解释。
- 这是**功能需求而非附加项**——它是"一个人记账"这个决策能成立的前提。

### 4.2 录入的 3 秒原则

- 新建狗时只有 **编号/批次** 必填，其余可后补
- 卖出一只狗 = 点状态 + 输售价，两个动作
- 快捷支出按钮预设常用金额（油价、疫苗单价）
- 所有列表页支持"再记一笔一样的"

## 5. 技术架构

```
src/
  domain/       纯函数：成本、摊薄、保本价、分账、风险模拟   ← 有单元测试
  storage/      存储层接口（第 1 期实现：IndexedDB）
  state/        应用状态与领域函数编排
  ui/           页面与组件
```

- **构建**：Vite + React + TypeScript + Tailwind CSS
- **存储**：IndexedDB（照片存压缩后的缩略图，避免膨胀）
- **离线**：Service Worker 缓存整个应用，断网可用（`vite-plugin-pwa`）
- **安装**：加到手机桌面后全屏运行，与原生 App 无视觉差异
- **部署**：静态托管，需要 https 链接。候选（实施时确定）：
  - 腾讯云 EdgeOne Pages（免费额度，国内可访问）
  - 阿里云 OSS 静态网站（约几元/月，国内稳定）
  - Vercel（零配置，国内访问可能不稳定）
- **可扩展口**：`storage/` 是一层接口。将来若改为云端同步，只需替换实现，`domain/` 与 `ui/` 不动。

**这是唯一可能产生费用的环节**（约 0～几元/月）。

## 6. 测试策略

**算错钱是本项目唯一不可接受的失败。** 因此：

1. **单元测试（vitest）覆盖 `domain/` 全部纯函数**，重点用例：
   - 损耗摊薄：3.6 节的 8 只案例必须精确得出 973
   - 指标 A 与指标 B 在部分死亡、部分售出时各自的值
   - `aliveCount === 0` 不崩溃（整批死光）
   - `inStockCount === 0` 时不显示指标 A
   - 退狗（`returned`）：退款支出 + 回到在库，医疗成本不冲销
   - 垫付与报销的冲销
   - 五种流水对四本账的影响（逐条对照 3.3 的表）
   - 分账比例之和不为 1 时保存被拒绝
   - **检疫阶段推导**（3.7）：六个阶段各自一例，含"接种未满 `rabiesWaitDays` 天"与"证明刚好在有效期末尾"两个边界
   - **`isSellable` 铁律**：只有 `certified` 为 `true`；`cert_expired`、`waiting_cert`、`unvaccinated` 全部为 `false`
   - **出栏检查清单**：一批 8 只、其中 3 只无有效证明时，清单恰好列出那 3 只
   - **渠道对照**（3.8）：同一批狗在两条渠道下算出的保本单价不同；每条渠道的额外成本与固定成本都被计入；`undecided` 渠道不产生额外成本（等于 3.5 的基准值）
   - **渠道算法不重复**：渠道对照内部必须调用与 3.5 同一个"每只存活狗真实成本"函数，不允许另写一套
2. **手动验证清单**：真实手机浏览器上走一遍完整流程（建批次 → 收狗 → 记支出 → 卖出 → 死亡 → 出对账单 → 导出备份 → 清空 → 导入恢复）
3. **数据恢复演练**：备份文件必须能真正恢复，这是纸上谈兵最容易出错的地方

| **手机与电脑数据不一致** | 本地存储是"一台设备一份"，不会自动同步 | 约定以手机数据为准，电脑只用于存放备份文件 |

### 7.1 引流链路合规性（链路待定）

第一条硬事实：**抖音小店卖活狗这条路，门是关着的。**「宠物生活 / 宠物活体 / 狗活体」在行业规范里是**暂停招商**。

第二条硬事实：**「抖音发视频引流、加微信成交」是平台写明了要罚的做法**，不是灰色地带。禁止项明确包含微信号、二维码，以及「主页加微」「私信我」「看个性签名」这类变体，处罚上限是永久封禁账号。

**两条路同时堵着。这不是写软件能解决的问题，是商业决策。** 本工具能做、也已经做的只有三件事：

1. 把检疫与病死犬无害化处理两笔法定支出算进保本价（D9）；
2. 在设计文档里把这条链路标为「待定」，**不让第二期在一条不存在的路上修路标**；
3. 把两条路的合规原文与来源如实摆出来，交给你和合伙人判断。

**在链路确定为合规方案之前，「内容与流量归因」（第 9 节第 3 项）不得开工。**

> 一个必须说清的适用性细节：上述导流条款的主体表述是「**达人**在通过购物车分享商品的过程中」，最直接约束的是**开通了商品分享/带货功能的账号**；纯内容账号主要依《抖音社区自律公约》与《用户服务协议》处理。但这**不是安全区**——协议保留暂停/终止服务的权利，公约禁止大量重复发布无特定目标的内容，第三方观察也显示 2024–2025 抖音与小红书都在收紧私域导流。**别把「还没被封」当成「不违规」。**

1. **客户线索跟进** —— 当咨询量起来后。设计方向：3 秒录入 + 到点提醒，而不是完整 CRM
2. **售后退款 / 包赔** —— 当第一例索赔发生后，按真实流程设计
3. **内容与流量归因** —— **链路待定（见上方警告）**。确定合规链路后再设计：手工录入视频数据（播放/咨询数）与成交的关联
4. **云端同步** —— 若两人需要实时共享或数据丢失风险变得不可接受，替换 `storage/` 实现即可
5. ~~**检疫流程台账**~~ —— **已于修订二（D12）提前到第一期**，见 §3.7 与第 4 节「检」标签页。原因：无论走哪条销售渠道都必须有检疫证明，它不是"等货源模式变了再说"的功能。这是二期清单里唯一被提前的一项。

## 10. 待用户确认的开放问题

- 项目名称（暂用"狗账"）
- 两位合伙人的称呼与分成比例（默认各 50%）
- 成本项最终清单（当前为：收购价、运输 + 笼具、疫苗驱虫医疗、**检疫（抗体检测 + 申报）**、**病死犬无害化处理**；损耗自动计算）
- **各个渠道的实际成本**：犬市摊位费/进场费、宠物店的收购价水平、有没有走活体物流的渠道及单价（见 3.8 与 10.1 第 6 条）。渠道对照功能需要这些数字才不是空壳。
- **本地检疫的两个天数**：`rabiesWaitDays`（默认 21，**非法定值，见 §3.7**）与 `quarantineLeadDays`（默认 3，法定：《动物检疫管理办法》第八条第二款 +《犬产地检疫规程》4.1）在软件里是可改的设置项，等你打听到本地实际要求后填真值。

### 10.1 必须由用户当地核实的 6 件事

这几件事软件**不能**替用户假设，必须打一个电话或跑一趟。问清之前，保本价里有好几个数字只能是 0，算出的价格会偏低（检疫费、病死犬处理费，以及各渠道的额外成本）。
