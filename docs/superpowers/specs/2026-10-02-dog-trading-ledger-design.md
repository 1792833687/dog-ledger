## 1. 背景

两位合伙人准备开始一门生意：**在本地收购小狗，再卖出去。** 目前处于**开张前筹备期（0 单）**。

> ⚠️ **原定链路已不可用。** 最初设想是"通过抖音引流（短视频/评论区/私信）→ 加微信 → 微信成交"。合规调研查明：抖音**明文禁止**站外导流（含微信号、二维码及各类变体），处罚上限为永久封禁账号；而「宠物活体 / 狗活体」类目在抖音电商**暂停招商**。详见 §7.1、§9 与 `docs/compliance/2026-10-02-犬只交易合规要点-平台篇.md`。**销售渠道是一个尚未解决的商业决策。**

合伙模式：**共同出资、共担风险、利润分成。**

用户在需求澄清阶段勾选了全部五个痛点维度（账目分钱、客户跟进、犬只台账、内容归因、售后口碑）。经讨论确认：**这五个维度是同一条业务流水线（收狗 → 医疗 → 拍摄 → 发布 → 咨询 → 成交 → 售后）的五个视角，不可能在第一版全部做好。**

### 1.1 核心矛盾

一笔生意都还没做，因此任何"记录 + 分析"工具都是空的。但**分钱规则、成本结构、损耗摊薄恰恰在开张前最该算清楚**——等 10 只狗卖完才发现分错，为时已晚。

因此第一版的定位不是"账本"，而是**决策台**：

> 先把会算错的账算对，再把会忘的事记住。

### 1.2 第一版要解决的唯一问题

**在出门看狗之前，知道自己最多能出多少钱，以及低于什么价格绝对不能卖。**

### 1.3 非目标（第一版明确不做）

| 不做的事 | 原因 |
|---|---|
| 客户线索跟进 / CRM | 0 单阶段没有线索可录，界面会空转 |
| 抖音内容与流量归因 | 抖音不开放私信/评论数据接口，无法自动归因；现在没有内容；**且这条引流链路本身合规性待定（见 7.1）** |
| 售后包赔 / 退货管理 | 尚未发生；等真实发生后再按真实流程设计 |
| 多人实时同步 | 用户选择"一人记账"，不需要服务器 |
| 微信小程序 | 用户选择"不卡形式，好用优先"；小程序需主体资质与审核，对内部工具是纯负担 |
| 库存出栏周期分析 | 缺少数据，且与核心目标无关 |
| **删除批次、删除单只狗** | 批次与狗是账目的"主体"，一笔流水一旦挂上去就必须能查到它属于哪一批哪一只（3.11 的删除弹窗就是要把这个说清楚）。狗只会因为卖、死、退回而离开在库，批次只能被"清空"而不是被删掉。3.9 说已经收货的预定单不能删，依据就是这一条 |
| **清空本机数据（一键重置）** | 数据只在手机上，误触一次就是全部账目归零；真要清空用开发者工具或浏览器的"清除站点数据"。备份与恢复见 5 |

## 2. 关键决策与理由

| # | 决策 | 理由 |
|---|---|---|
| **D1** | 交付形态为**纯前端 PWA**（手机浏览器打开 + 加到桌面），不是微信小程序 | 这是内部记账工具，不是给客户看的。小程序正式发布需企业/个体户主体（认证费 300/年）与审核周期；PWA 零资质、零审核、当天可用。将来若要小程序，只需再包一层壳。 |
| **D2** | 数据存**本机 IndexedDB**，无后端、无账号、无月费 | 用户明确选择"我一个人记账就行，伙伴偶尔看结果"。换来零成本零维护。**代价是数据只存在一台设备上，必须靠手动备份保证安全**（见第 7 节，这是本项目最大的风险）。 |
| **D3** | 第一版范围 = **保本决策台 + 犬只批次台账 + 资金流水 + 分账报表** | 这是唯一在 0 单阶段立即有价值的组合。软件的价值来自数据密度，不是功能数量。 |
| **D4** | **批次**是损耗摊薄的计算单位，不是单只狗 | 死亡、运输、疫苗都是"一趟一批"发生的。死亡的个体是谁不重要，重要的是这批死了几只、活了几只、损失摊给谁。平铺成单表则无法表达。 |
| **D5** | **垫付 ≠ 出资**，两者必须分开记 | 合伙最常见的错账。A 出门收狗先垫 5000 现金是垫付（要从池子报销还给 A）；A 往池子打 5000 入伙是出资（本金）。混记则三个月后无法算清。 |
| **D6** | 所有金额计算写成**纯函数**，存储层做薄接口封装 | 为将来"两人实时共享"留口：届时只需把存储层从本地换成云端，界面与算法一行不改。 |
| **D7** | **流水（LedgerEntry）是唯一的真相来源**，狗与批次只是分类维度 | 避免"狗的售价存在狗表、同时在流水里又记一笔收入"这类双写不一致。售价由关联到该狗的收入流水推导。 |
| **D8** | 录入必须"**3 秒原则**" | 用户已经指出：录一条要 30 秒，两天后就不会再录。所有录入路径都要先想清楚最少字段。 |
| **D9** | **检疫与病死犬无害化处理进成本模型**，作为两个独立的内置成本项 | 合规调研（`docs/compliance/`）查证：检疫是出售的**法定前置**，不是可选的合规开销；病死犬无害化处理是强制支出。这两笔钱是真金白银的现金流出，把它们排除在外的"保本价"是错的。**它们与"损耗摊薄"必须分开理解**：摊薄是账面重分配（一分钱没多花），检疫与处理是真支出（钱出去了）。 |
| **D10** | **不替用户做商业决策，但把合规事实摆到明面上** | 抖音明文禁止站外导流、狗活体类目暂停招商——这两件事都不是写软件能解决的。软件能做的：把合规成本算进保本价，并把"引流链路待定"写进文档，避免第二期给一条不存在的路修路标。改动已批准的设计须先经用户同意（本次已获批准）。 |
| **D11** | **批次必须记「计划去向」，并能按渠道分别算保本价** | 线下成交是唯一走得通的路径（见 7.1），而各渠道成本结构差别极大：卖断给宠物店几乎无额外成本，自零售要承担退狗与售后，犬市要摊场地费与往返油费，平台电商要包装 + 有轨迹物流 + 死亡赔付。如果只有一个笼统的"批次成本"，用户无法回答"这批走哪条路更划算"。**渠道清单刻意不含任何抖音选项**——那两条路已被查证堵死，留在选项里等于诱导。 |
| **D12** | **检疫流程台账提前到第一期** | 检疫是每一单出售的法定前置；一证多用（数量超出载明部分、种类不符、使用转让的证明）按"未经检疫"处理，落进货值 15~30 倍那一档，负责人 5 年禁业。**没有地方记录证明编号与有效期，就只能靠脑子记——这正是最贵的那类遗忘。** 原计划把它放第二期，前提是"货源可能转为与繁育基地签约"；现在前提变了：无论走哪条渠道都必须有证明，所以它是第一期的关键路径，不是可选功能。 |
| **D13** | **预定单（`PreOrder`）是独立的平级数据，不是"没有狗的批次"** | 真实业务是先去村里看狗、谈好、约日子再回来收（"找到的狗还没有合适的年龄段就预定了，一般都是两个月大的小狗，等长到两个月大我们会去收"）。预定单**没有狗、没有成本、不进任何批次统计**。塞进 `Batch` 会让"批次盈亏排行""死亡率""成本摊薄"到处都要加过滤条件，那是算错钱的标准入口。代价是要给已录入的老数据写一次补齐默认值（见 3.9 与 D16）。 |
| **D14** | **先做、后补账：建批次只记收购款，其余成本事后一张表补** | 用户的原话是"我希望是我们先做后才生成账目表再记录的"。收货现场只有两个数是确定的（实收几只、每只多少钱）；运输、疫苗、检疫、处理费是之后才发生的。**先要求填全成本，等于逼人在最忙的时候编数字**（D8 的 3 秒原则）。补账表**只新增流水、不按项目替换**——替换会悄悄删掉用户在"钱"页手记的账，那是"账变少了却不知道为什么"的来源。代价是同一张表点两次会记两遍，因此表下必须常显"这一批目前已记成本合计"、点之前必须弹一句"将新增 N 笔流水"。 |
| **D15** | **流水可以改、可以删；删带狗的销售流水时，同一次操作把狗改回「在库」** | 录错一位数（1500 写成 15000）在手机上是高频事故，而原设计**没有任何修改或删除流水的入口**，只能靠"再记一笔对冲"，账会越来越脏。"收入没了、狗却还是已售"是自相矛盾的状态，以后算盈亏时找不到原因，所以删除与狗状态回退必须是**一次原子操作**。允许改的字段是金额/日期/备注/经手人/支出类别；**类型不可改**（支出不能改成注资，那等于换一笔账，请删掉重记）。 |
| **D16** | **读取时补齐默认值（`normalizeAppData`），不改备份文件格式** | 修订三给 `AppData` 加了新字段（`preOrders`）与新设置项。用户手机上已有真实数据（已上线的 GitHub Pages 站址），**任何"打不开"或"看起来被清空"都是本项目最严重的失败**（D2 的代价就是数据只在一台设备上）。因此：**本地读取路径**（`src/state/persistence.ts` 的 `loadPersistedData`，也就是 `storage.load()` 的唯一调用点）跑一个纯函数补齐缺失字段；`version` 保持 1，不做破坏性迁移。**导入备份走的是另一条路**（`src/storage/backup.ts` 的 `importBackup` 是"逐字重建白名单对象"，`Settings` 缺键已经由 `...DEFAULT_SETTINGS` 兜住，但**白名单外的顶层字段会被静默丢掉**）：因此那里必须显式补 `preOrders: data.preOrders ?? []`，补 `[]` 这种写法是错的——**导出含预定单、导入就丢**，而只测"导入旧格式备份"的用例会全绿通过 |

## 3. 领域模型

### 3.1 三个层次

```
池子（钱从哪来）
  └── 批次（一次收回来的货）
        └── 单只狗（独立成本、状态、成交）
```

### 3.2 实体定义

> **本块是概念草图，不逐条追平实现。** 权威接口以 `src/domain/types.ts` 为准（修订二加入的 `Batch.plannedChannel`、`Dog` 的 6 个检疫字段、`Settings.rabiesWaitDays` / `quarantineLeadDays`，以及修订三加入的 `AppData.preOrders` / `Settings.preOrderLeadDays`，都以代码为准；本节只解释它们的含义）。

```ts
// ---- 设置 ----
type Settings = {
  partners: { id: string; name: string; shareRatio: number }[]  // shareRatio 之和为 1
  costItems: CostItemDef[]        // 可配置成本项
  targetMarginRate: number        // 目标毛利率，用于建议售价，默认 0.3
  expectedMortalityRate: number   // 预估死亡率默认值，用于决策台，默认 0.15
}

type CostItemDef = {
  id: string
  name: string                    // 如"收购价""运输+笼具""疫苗驱虫医疗"
  scope: 'batch' | 'dog'          // 这笔钱发生在批次层面还是单只狗层面
  isBuiltin: boolean              // 内置项不可删除，只能改名
}

// ---- 批次 ----
type Batch = {
  id: string
  name: string                    // 如"10月3日 李村一批"
  date: string                    // ISO 日期
  source: string                  // 货源：农户 / 养殖场 / 同行 / 其他
  note: string
  status: 'active' | 'closed'     // closed 后不再计入"在库"
}

// ---- 单只狗 ----
type Dog = {
  id: string
  batchId: string
  code: string                    // 编号，如 "1003-1"
  breed: string
  sex: 'male' | 'female' | 'unknown'
  ageMonths: number | null
  status: 'in_stock' | 'sold' | 'dead' | 'returned'
  note: string                     // 修订三起：备注只存文字，不存照片（见 3.9 的说明）
}

// ---- 资金流水（唯一真相来源）----
type LedgerEntry = {
  id: string
  date: string
  type: 'injection' | 'expense' | 'income' | 'reimbursement' | 'distribution'
  category: string                // expense 关联 CostItemDef.id；income/distribution 用固定值
  amount: number                  // 恒为正数，方向由 type 决定
  paidBy: 'pool' | string         // expense 专用：池子直付 或 某合伙人垫付
  payee: string | null            // reimbursement / distribution 专用：收款人 partnerId
  batchId: string | null
  dogId: string | null
  note: string
}
```

### 3.3 五种流水对四本账的影响

项目维护四本账：**池子现金（cash）**、**垫付账（advance）**、**注资本金（capital）**、**分红账（distributed）**，外加一套**损益**统计。

| 类型 | 池子现金 | 垫付账 | 注资本金 | 分红账 | 损益 |
|---|---|---|---|---|---|
| `injection` 注资 | +amount | — | 注资人 +amount | — | — |
| `expense` 支出（池子直付） | −amount | — | — | — | 成本 +amount |
| `expense` 支出（某人垫付） | 不变 | 垫付人 +amount | — | — | 成本 +amount |
| `income` 收入 | +amount | — | — | — | 收入 +amount |
| `reimbursement` 报销 | −amount | 收款人 −amount | — | — | — |
| `distribution` 分红 | −amount | — | — | 收款人 +amount | — |

**关键设计：分红是可选的。** 如果两人决定把利润留在池子里继续周转，就**不记** `distribution`。报表仍然显示"应分未分权益"，钱留在池子里当本金。这避免了"必须先把钱拿出来再打回去"的荒谬流程。

### 3.4 计算规则（全部为纯函数）

> 约定：单只狗层面的支出（收购价、疫苗）在一笔流水上**同时写入 `batchId` 与 `dogId`**。因此它既计入批次总成本，也能被单独取出。这是 3.3 "流水是唯一真相来源" 的落地方式。

```ts
// ---- 基础取数 ----
dogOwnCost(dogId)         = Σ expense(dogId = d).amount
batchTotalCost(batchId)   = Σ expense(batchId = b).amount   // 含批次层面与单只狗层面
batchIncome(batchId)      = Σ income(batchId = b).amount
inStockCount(batchId)     = count(status = 'in_stock' | 'returned')   // 退狗回到在库（见 3.4 边界规则）
aliveCount(batchId)       = count(status ≠ 'dead')          // sold 与 returned 都算活着
deadLoss(batchId)         = Σ dogOwnCost(d) for d.status = 'dead'

// ---- ★ 指标 A：批次剩余保本单价（决策用）----
// 回答："剩下的每只至少卖多少钱，整批才不亏"
remainingFloorPrice(batchId) = max(0, batchTotalCost − batchIncome) / inStockCount
// inStockCount = 0 时不显示；结果 = 0 时显示"已回本，剩下的都是利润"

// ---- ★ 指标 B：单只狗摊薄成本（复盘用）----
// 回答："这只狗算上死掉的同伴，真实花了多少钱"
// 摊的是【整批的钱】÷【还活着的只数】，含运输、病死犬处理这类批次层面的支出。
// 不能写成 dogOwnCost + deadLoss/alive：那个式子漏掉批次层面的钱，
// 会让 3.6 案例算出 906.67 而不是 973.33，"真实成本"就名不副实了。
dilutedCost(dogId) = batchTotalCost(batchId) / aliveCount(batchId)
                     // aliveCount = 0（整批死光）时退化为 dogOwnCost(dogId)，不得除零
dogProfit(dogId)   = income(关联到该狗的收入之和) − dilutedCost(dogId)

// ---- 资金三账 ----
poolBalance(entries)        = Σ injection + Σ income − Σ expense(paidBy = 'pool') − Σ reimbursement − Σ distribution
advanceBalance(partnerId)   = Σ expense(paidBy = partnerId) − Σ reimbursement(payee = partnerId)
contributedCapital(partnerId) = Σ injection(partnerId)
distributedTo(partnerId)    = Σ distribution(payee = partnerId)

// ---- 损益与分账 ----
netProfit(from, to)   = Σ income − Σ expense
claimable(partnerId)  = (netProfit 累计 × shareRatio(partnerId)) − distributedTo(partnerId)
```

**为什么需要两个指标（A 和 B）？**
它们回答的是两个不同的问题，不可互相替代：

- **A 面向未来的现金流**："我还差多少回本，剩下的狗必须卖多少钱。" 它随成交实时下降，可归零，极其实用。
- **B 面向过去的经济学**："这批到底赚没赚。" 它把死狗的成本摊到每只活着的狗头上。

用 A 去复盘，已售狗的盈亏会随后来的死亡而变动，越看越乱；用 B 去决策，最后一个买家就要独自承担全部损耗，报价会高得卖不出去。**界面上必须把两者的场景标注清楚。**

### 3.5 决策台模拟公式（还没有批次时使用）

| 输入 | 符号 |
|---|---|
| 预计收到几只 | `n` |
| 每只收购价 | `p` |
| 这趟油费 + 笼具 | `f` |
| 每只疫苗医疗 | `v` |
| **每只检疫费**（抗体检测 + 申报跑腿） | `q` |
| **每只病死犬处理费** | `d`（默认取 `settings.disposalPerDog`） |
| 预估死亡率 | `m`（默认取 `settings.expectedMortalityRate`） |
| 打算卖多少钱 | `s` |

```
预估存活数   = n × (1 − m)
预估死亡数   = n × m
预估总成本   = n × p + f + n × v + n × q + (n × m) × d
                 ↑ 检疫费按【买回来的全部只数】交：狗死了检疫的钱也不退
                                        ↑ 处理费只对【预估死亡】的那部分发生
预估摊薄成本 = 预估总成本 ÷ 预估存活数        ← ★ 这就是保本价
建议售价     = 预估摊薄成本 × (1 + targetMarginRate)
风险模拟(k)  = 若只卖掉 k 只 → 亏损 = 预估总成本 − k × s；每人承担 = 亏损 ÷ 2
```

> ⚠️ **`q` 与 `d` 默认值都是 0，代表"还不知道"，不要当成"不用花钱"。**
> 填 0 时算出的保本价是**偏低**的。这两个数字必须由用户向当地动物卫生监督机构问清后在「设置」里填一次。
> 软件不能编一个看起来合理的数字——那会让人以为算过了。

**边界规则（必须有测试覆盖）：**
- `aliveCount === 0`（整批死光）→ `dilutedCost` 退化为 `dogOwnCost`，除零不得崩溃，界面显示"全损"警告
- `inStockCount === 0`（全部售出）→ 不显示指标 A，只显示指标 B 的最终复盘
- 批次未结束时 `deadLoss` 与 `batchIncome` 都在变，说明**已售出狗的盈亏是浮动的**，界面必须显式标注"按当前损耗率估算"
- `returned`（退狗）的记账方式：狗回到在库（计入 `inStockCount` 与 `aliveCount`），**已发生的医疗成本不冲销**，同时记一笔 `expense`（类别"售后退款"，金额 = 退回给客户的款）关联到该狗。若狗没要回来，则状态保持 `sold`，只记退款支出。
- **退回的狗后来又死了 → 那笔退款不冲销。** 这时账上会同时有三笔：`income/售出`(P)、`expense/售后退款`(P)、以及计入 `deadLoss` 的购置成本 C 与已发生医疗成本 M。这是**对的**：P 与 P 相互抵消，真实亏损 = −(C+M)。若再去冲销退款，P 会被当成净收入留下，账面凭空多出一笔 P 的假利润——比不冲销错得更厉害。批次净利按 `income − totalCost` 算（`src/domain/costing.ts:107`），`deadLoss` 只是展示与摊薄的输入，**不参与净利计算**，不会二次扣除。
- **退款流水的改正（2026-10-03 修订三已纳入第一期，取代此前"第一期不做流水纠错"的限制）**：任何一笔流水都能改金额 / 日期 / 备注 / 经手人 / 支出类别，也能删除（见 §3.11）。`aftercare_refund` 金额填错时，直接改那一笔即可，不再只能看着「已记退款」。⚠️ 两条注意：①删掉一笔退款支出**不会**自动改变狗的状态（退款流水不是"狗在哪"的决定者），界面必须提示用户自己去核那只狗；②`src/ui/dogLedger.ts` 的 `refundedCurrentSale` 依赖 `entries` 的**追加顺序**——复核结论是**这一处不需要改**（`updateEntry` 不重排数组、`deleteEntry` 是物理删除，追加顺序这个前提仍然成立；改成按 `date` 找反而会打挂同日"卖→退款→又卖出"的既有回归，见 §3.11 末尾）。
- 分红比例之和 ≠ 1：保存设置时校验并拒绝

### 3.6 关键案例（用于验证算法与用户沟通）

收购 8 只 × 600 = 4,800；运输 + 笼具 400；疫苗驱虫医疗 8 × 80 = 640；批次总成本 **5,840**。

死亡 2 只，存活 6 只 → 每只存活狗真实成本 = 5,840 ÷ 6 = **973**。

若按收购价思维以 900 卖出，**每只亏 73**，而当事人会以为赚了 300。这是本项目存在的核心理由。

**再加上合规成本（用占位假设：检疫 50 元/只、病死犬无害化处理 200 元/只）：**

检疫 8 × 50 = 400（按买回来的全部 8 只交，死的那 2 只的检疫钱不退）；病死犬处理 2 × 200 = 400。

批次总成本 **5,840 + 800 = 6,640**，存活 6 只 → 每只存活狗真实成本 = 6,640 ÷ 6 ≈ **1,106.67**。

| | 不含合规成本 | 含合规成本 | 差 |
|---|---|---|---|
| 每只存活狗成本 | 973.00 | 1,106.67 | +133.67（**+13.7%**） |
| 以 900 卖出，每只 | 亏 73 | **亏 206.67** | — |

> ⚠️ 上面的 50 元 / 200 元**只是占位假设，不是查到的价格**，仅用于说明量级。
> 真实数字必须由用户向当地动物卫生监督机构问清后填进「设置」——软件不替用户编价格。

### 3.7 检疫台账（合规关键路径）

检疫证明是**每一单出售的法定前置**，不是可选步骤。这一节的规则决定「狗」页面能不能在出事之前把人拦住。

**每只狗要记的 6 个字段**（`Dog` 接口，见 3.2）：

| 字段 | 含义 | 为什么要有 |
|---|---|---|
| `rabiesVaccinatedOn` | 狂犬病疫苗接种日期 | 疫苗是申报检疫的前置，也是"最早可送检日"的起点 |
| `antibodyTestedOn` | 免疫抗体检测日期 | 犬比猫多这一道；没有报告原件不予受理 |
| `antibodyReportNo` | 抗体检测报告编号 | 报告原件会丢，编号不会 |
| `quarantineCertNo` | 《动物检疫合格证明》编号 | **一证多用要按货值 15~30 倍罚**，编号是唯一能自证"哪只狗配哪张证"的东西 |
| `quarantineCertIssuedOn` | 证明签发日期 | 用于计算有效期 |
| `quarantineCertValidUntil` | 证明有效期至 | **过期即不可出售**，必须能在列表上直接看到 |

**两个时间参数做成设置项，不写死在代码里**（`Settings`）：

- `rabiesWaitDays`（默认 21）—— 免疫后需等待的天数。⚠️ **这个 21 不是法定天数**：2026-10-02 取到《犬产地检疫规程》与《狂犬病防治技术规范》两份官方原文后复核，**两份文件里都没有「21 天」**（规程只说「在有效保护期内」，技术规范只说「每年加强免疫一次」）。它更可能是抗体检测的实验室采样窗口要求。做成可配置就是为了让你问清之后改，而不是让软件替你猜。详见 `docs/compliance/2026-10-02-犬只交易合规要点-法规篇.md` §2.9。
- `quarantineLeadDays`（默认 3）—— 申报检疫需提前的天数，《动物检疫管理办法》第八条第二款。

**每只狗由这 6 个字段推导出一个阶段**（纯函数，`domain/quarantine.ts`）。

**判定次序本身是业务规则，不是实现细节**（2026-10-03 裁定后修订；下表按实际判定次序排列，第一个命中的即为结果）：

| 序 | 阶段 | 判定 | 下一步该做什么 |
|---|---|---|---|
| 1 | `cert_expired` | `quarantineCertNo` 非空 **且** `quarantineCertValidUntil < 今天` | **必须重新申报**，不能靠旧证出售 |
| 2 | `certified` | `quarantineCertNo` 非空 **且** `quarantineCertValidUntil` ≥ 今天 | 可以出售 |
| 3 | `unvaccinated` | `rabiesVaccinatedOn === null` | 去打狂犬疫苗 |
| 4 | `waiting_cert` | 已有抗体检测记录，但没有检疫证明 | 准备申报（提前 `quarantineLeadDays` 天） |
| 5 | `ready_to_test` | 已接种且已满 `rabiesWaitDays` 天，`antibodyTestedOn === null` | 去采血做抗体检测 |
| 6 | `waiting_antibody` | 已接种，但距接种不足 `rabiesWaitDays` 天 | 等（显示还要等几天） |

**为什么「有证明」要排在「没接种」前面**（这是被明确裁定过的，不是随手排的）：

1. **检疫证明本身就是出售的法定许可**。《动物防疫法》第二十九条禁止的是「未附有检疫证明」而出售；《犬产地检疫规程》5.1 是**逐只出具**动物检疫证明，而拿到这份证明的前提，规程 3.3 已经写明是「按规定进行狂犬病免疫，并在有效保护期内，且狂犬病免疫抗体检测合格」。也就是说**证明是免疫与抗体检测都已满足的下游产物——它存在就蕴含上游满足**。台账里 `rabiesVaccinatedOn` 那一格是给自己看的便利记录，**不是出售的前置条件**。
2. **反过来排会给出与事实相反的行动指令**。从繁育基地接手一只「证随狗走、接种日期不详」的狗是真实场景，软件却说「先带去接种狂犬疫苗」并挡住出售——它会推着你为一只已经合法的狗白花钱打一针，同时让台账看起来是坏的。
3. **反过来排还会丢信息**。「证明已过期、但接种日期没填」的狗会被判成 `unvaccinated`（= 从没打过疫苗），而不是 `cert_expired`（= 必须重新申报检疫）。后者才是你真正需要知道的下一步。

**「有证明」两个条件必须都齐**：只有编号没有有效期、或只有有效期没编号，都当**没有证明**，继续往下判。`quarantineCertNo` 是这份证明的凭据，没有编号就无法把它与任何一份文件对上。

**一条铁律**：`isSellable(dog, today)` 只有在 `certified` 阶段才返回 `true`。批次出栏前的检查清单（`preSaleChecklist(data, batchId, today)`）要能把"这批 8 只里有 3 只没有有效检疫证明"直接摆出来——**这是本工具唯一能防止 5 万级罚款的地方。**

> ⚠️ 本节的日期与天数是**提示**，不是法律意见。真正的准绳是当地动物卫生监督机构的答复（见 10.1）。

### 3.8 渠道对照（同一批狗，不同渠道不同保本价）

销售环节已确认只可能发生在线下（见 7.1），而**各渠道的成本结构差别极大**：卖断给宠物店几乎无额外成本；自零售要承担退狗与售后；犬市要摊场地费与往返油费；平台电商要包装、有轨迹物流与死亡赔付。

因此：

- `Batch` 新增 **`plannedChannel: ChannelId`**（默认 `'undecided'`），记录这批狗打算走哪条路。
- `SALES_CHANNELS` 常量列出 9 条渠道（含"未定"），**渠道清单里刻意不含任何抖音选项**——留着会诱导人去走那条会被永久封号的路。每条渠道带一句 `note` 说明其特有成本或风险。
- 决策台新增**渠道对照**：对若干候选渠道分别输入"预期单价 / 每只额外成本 / 该渠道专属固定成本"，输出每个渠道的**每只利润**与**可接受的最低单价（保本单价）**，并标出哪个渠道在给定价格下是亏的。

**渠道对照与 3.5 的决策台共用同一套成本模型**：先算出"每只存活狗的真实成本"（含检疫，见 3.5），再叠加各渠道的额外成本，最后对比单价。**不允许出现"渠道单独一套算法"**——那正是算错钱的地方。

### 3.9 预定单（还没变成批次的狗）

> 本节与 3.10、3.11 由**修订三**新增。3.2 的代码块是概念草图，**权威接口以 `src/domain/types.ts` 为准**。

真实业务形态：先去村里看狗、谈好，狗还小（一般两个月大才收），约好日子再回来收。**预定单是"还没变成批次的狗"**，与批次、狗平级，不进任何批次统计。

**存储字段**（`AppData.preOrders: PreOrder[]`）：

| 字段 | 含义 | 必填 |
|---|---|---|
| `id` | 内部标识 | — |
| `sellerName` | 卖家是谁（"老李家""邻村张姐"，一句话即可） | 必填 |
| `sellerContact` | 怎么联系（电话或微信号，自由文本） | 选填 |
| `expectedCount` | 约了几只 | 必填 |
| `collectDate` | 约好什么时候去收（`'YYYY-MM-DD'`） | 必填 |
| `traits` | 品种 / 毛色 / 公母等特征（一句话） | 选填 |
| `note` | 备注 | 选填 |
| `createdAt` | 记下这条的时间（完整 ISO datetime） | 自动 |
| `status` | **只存三态**：`'reserved' \| 'received' \| 'cancelled'` | 自动 |
| `receivedCount` | 实收几只（收货后才有） | 收货时填 |
| `receivedBatchId` | 收到了哪个批次（收货后才有） | 自动 |
| `cancelReason` | 黄了的原因（一句话） | 取消时填 |

**明确不记**（用户裁定）：**说好的单价、已付定金、照片**。照片不存的理由：数据全在浏览器里，备份是唯一保险，存照片会把备份从几十 KB 变成几 MB。定金与约定单价将来要记再加。

**界面上你看到的是四个状态**（预定中 / 该去收了 / 已收货 / 黄了），但只有两个是**存储**状态——"预定中 / 该去收了"是**按日期算出来的**（纯函数 `preOrderStage(order, today, leadDays)`），不需要用户天天手动改：

| 派生阶段 | 判定（按序，第一个命中即结果） | 界面文案 |
|---|---|---|
| `cancelled` | `status === 'cancelled'` | 「黄了」+ 原因 |
| `received` | `status === 'received'` | 「已收货」+ 指向那个批次 |
| `overdue` | 今天 **晚于** `collectDate` | 「已经过期 N 天」 |
| `due_soon` | 今天 ≥ `collectDate` 减 `leadDays` 天 | 「还有 N 天去收」/「今天去收」 |
| `upcoming` | 其余 | 只显示日期与只数 |

> `overdue` 与 `due_soon` 在界面上是**同一个「该去收了」**（都会挂到「狗」页顶部），只是文案不同。**到日子那天算「今天去收」，晚一天才算过期。**

`leadDays` 来自新设置项 **`Settings.preOrderLeadDays`（默认 3）**，与 `rabiesWaitDays`、`quarantineLeadDays` 同样是可改的设置，不写死在代码里。

**收货是一次原子操作**（`receivePreOrder(data, preOrderId, { name, date, receivedCount, unitPriceFen })`），用户只填三个数（实收几只默认等于约定只数、每只多少钱必填可为 0、日期默认今天），一次做完四件事：

1. 建批次（名字沿用现有规则「收狗 6 只 14:30」，**只数用实收只数不是约定只数**——名字写的是这一批实际有几只狗；`plannedChannel` 默认 `'undecided'`；`source` 存卖家名，`note` 写「来自预定单：老李家」）；
2. 按实收只数建狗（`code` 规则不变：`${批次名}-${序号}`）；
3. 记收购款（**每只一笔** `expense` / `category: 'purchase'`）；**单价为 0 时一笔都不写**（与 `planning.ts:116` 的既有口径一致：0 元的支出没有信息量），所以"个别狗价钱不同可以单独改"只对单价 > 0 的批次成立；
4. 这张预定单 `status → 'received'`、`receivedCount`、`receivedBatchId` 落库。

**实收少于（或多于）约定**只做提示与留痕，不阻止、不自动摊到别的批次。**差额在收货那一刻算一次、写成批次 `note` 的快照**（「比约定的少 2 只」），**不在界面上现算**——现算会让"改一个数字"导致历史留痕凭空出现或消失。

**守卫**：`preOrderId` 不存在、`status !== 'reserved'`（已经收了或已经黄了）、`receivedCount < 1` —— 三种都返回**同一引用**（`actions.ts` 既有约定：守卫不通过就什么都不做，不抛错）。注意与 `addExpense` 的区别：那里对非法金额是 `Math.max(0, Math.round())` **夹取**，而"单据状态不对"必须是"不动作"。

**能改、能删**：可改字段白名单＝`sellerName` / `sellerContact` / `expectedCount` / `collectDate` / `traits` / `note`（`updatePreOrder`）。**`status` / `receivedCount` / `receivedBatchId` 只能由收货与取消两个动作写入**，界面不给直接编辑——否则用户能把「已收货」改回「预定中」，绕过上面的守卫，同一张预定单收两次、建出两个批次。记错了可以整条删掉（`deletePreOrder`）。**例外**：已经「已收货」的预定单不能删，而且六个可改字段里**只允许再改 `note`**（它连着那个批次，改只数之类的数字会让批次上的留痕对不上）；要撤只能先处理那个批次（本版不支持删批次与删狗，见第 1.3 节非目标里新增的两条）。

**其余的钱不在收货时问**（运输 / 疫苗 / 检疫 / 处理费），回来按 3.10 补。

### 3.10 先做、后补账

**取代**原设计「点『就按这个收』即生成全部成本流水」的做法（D14）。

收货那一刻只记收购款（3.9），**账上只记真花了的钱**。回来之后在批次详情页填一张表：

| 表里的行 | 输入口径 | 生成的流水 |
|---|---|---|
| 这趟油费 + 笼具 | 批次一个数 | **1 笔**（`category: 'transport'`） |
| 每只疫苗、驱虫、医疗 | 每只一个数 | **每只一笔**（`category: 'medical'`） |
| 每只检疫（抗体检测 + 申报） | 每只一个数，预填设置里的默认值 | **每只一笔**（`category: 'quarantine'`） |
| 每只病死犬无害化处理费 | 每只一个数，只填真花了的 | **按已标「死亡」的只数**每只一笔（`category: 'disposal'`） |

**四行填 0 就是"这笔没花"，一笔流水都不写**（与 `planning.ts:98/116/119/123` 的既有口径一致）：0 元的支出没有信息量，写进去只会让流水表变脏。

接口（`src/domain/planning.ts`）：

```ts
addBatchCosts(data, input: {
  batchId: string; date: string
  transportFen: Money; medicalPerDogFen: Money
  quarantinePerDogFen: Money; disposalPerDogFen: Money
}): AppData

previewBatchCosts(data, input: {
  batchId: string
  transportFen: Money; medicalPerDogFen: Money
  quarantinePerDogFen: Money; disposalPerDogFen: Money
}): { count: number; totalFen: Money }
```

`date` 由界面传「今天」（域层一律不许 `new Date()`）；记录一律 `paidBy: 'pool'`（**真的有人自己垫了钱，记完去「钱」页改那一笔的经手人**，见 3.11）；`disposal` 按**点击那一刻**已标「死亡」的只数取快照——之后又死了一只，必须再补一次（这条写进 §10 开放问题）。

三条硬规则：

1. **疫苗与检疫按这一批全部狗算**（死掉的狗生前也打过针），**处理费只按已标死亡的狗算**。
2. **只新增、不替换**：补账表不会去删或改任何已有流水（包括用户在「钱」页手记的账）。因此**同一张表点两次会记两遍**——表下必须常显「这一批已记成本 ¥X · 共 N 笔（含收购款）」，点之前必须弹一句「将新增 N 笔流水，共 ¥X」。两处数字的**口径写死**：表下的 ¥X ＝ `batchTotalCost(data, batchId)`、N ＝ 该批次 `type === 'expense'` 的流水条数，**两者都含收购款**；弹窗里的 N/¥X 只算**这一次要新增**的四行，用 `previewBatchCosts`。
3. **不假装保本价是准的**：该批次除收购款外还没有任何成本流水时，批次卡上显示橙字「这一批还没补成本，保本价现在是偏低的」。补过之后改显「已记成本 ¥X · 共 N 笔」。判定写成纯函数，判定式写死为

   ```ts
   !data.entries.some(e => e.type === 'expense' && e.batchId === batchId && e.category !== 'purchase')
   ```

   不能图省事用 `batchTotalCost(data, batchId) === 0`：`costing.ts` 的 `batchTotalCost` 只按 `type` 与 `batchId` 过滤、**不看 `category`**，收购款本来就记在里面。判定不许散落在界面里。

改错**统一交给 3.11 的流水编辑**（比"按项目替换"少一套逻辑，也不会悄悄删账）。

**补账表不得自己算成本**：它只产生流水，批次成本、每只存活狗真实成本、保本价仍然由既有的成本函数从流水现算（`src/domain/costing.ts` 是唯一算法）。与 3.8 的"不允许渠道单独一套算法"是同一条纪律。

**决策台（「算」页）的定位不变**，仍是"出门看狗之前算划不划算"：预计收几只、每只收购价、预估死亡率、打算卖多少 → 保本价与渠道对照。但底部的按钮变成**收货**：点开一个只有两个字段的弹窗（实收只数、每只收购价，两个都从表单里预填），确认后调

```ts
receiveBatch(data, input: {
  name: string; date: string; count: number
  unitPriceFen: Money; channel: ChannelId
}): AppData            // count < 1 → 返回同一引用，不建批次
```

**油费等估算值只用于算保本价，不写进账**。

**`createBatchFromPlan` 是删除，不是保留。** 修订三之后没有任何界面路径会"按估算一次性把全部成本写进账"：留着它就是一段只有测试在用的死代码，而且那个名字会让后来的人以为它才是建批次的正当入口。做法：

- 把它内部"建批次 + 按只数建狗 + 每只一笔收购款"那一段抽成 `addBatchWithDogs(data, input: { name, date, count, unitPriceFen, channel, source, note }): { data: AppData; batchId: string | null }`（`batchId === null` 表示没建，`count < 1` 时如此）；
- `receiveBatch` 与 3.9 的 `receivePreOrder` 都走它——**建批次与狗号 `${名}-${序号}` 的规则只有一处**；
- `plan()` / `PlanInput` / 保本价 / 渠道对照**全部不动**；
- `planning.test.ts` 里 `describe('createBatchFromPlan')` 的 12 条用例整体改写成 `addBatchWithDogs` / `receiveBatch` 的等价用例（"按只数生成流水"的笔数口径改由 `addBatchCosts` 的测试承担），覆盖率不降。

### 3.11 流水纠错（改与删）

原设计**没有任何修改或删除流水的入口**（见 §3.5 的第一期已知限制），只能"再记一笔对冲"，账会越来越脏。修订三把它纳入第一期（D15）。

**能改**（`updateEntry(data, entryId, patch)`）：`amount`、`date`、`note`、`paidBy`（池子 / 某人垫付）、以及 **`expense` 流水的 `category`**（疫苗记成运输了可以改回来）。

`amount` 沿用**全仓统一口径**：`Math.max(0, Math.round(x))` —— 与 `addExpense` / `sellDog` / `transferEntry` 一字不差。所以"0 元"是可改出来的（既有「钱」页本来就允许新增 0 元支出，`moneyBook.ts` 的 `canSubmit` 只要求能解析成数字）：**宁可口径一致，也不要在编辑路径上单独立一条"必须 > 0"的规矩**——那会造成"记得下、改不动"这种自相矛盾。界面负责拦"不是数字"（红字），域层负责夹取。

**不能改**：`type`、`id`、`batchId`、`dogId`。支出不能改成注资——那等于换一笔账，请删掉重记。改 `paidBy` **不额外拦截**（会把池子余额算成负数，这是既有裁定：账要如实反映"钱花超了"，见 Task 11b 的边界）。

**能删**（`deleteEntry(data, entryId)`），连带规则只有一条，但必须原子：

| 删的是 | 连带动什么 |
|---|---|
| 关联到狗的销售收入（`type === 'income'` 且 `dogId` 非空），**且它是该狗最后一条 `income` 流水**，且该狗当前状态是 `sold` 或 `returned` | **同一次操作把该狗 `status` 改回 `'in_stock'`**，「钱没了、狗还是已售」是自相矛盾的状态 |
| 关联到狗、但**不是**该狗最后一条销售流水 | **只删这一笔，不动狗状态**。一只狗可以先卖、退了款、又卖出去（`DogsPage.tsx` 的退狗按钮与 `dogLedger.test.ts` 都钉着这条路径）：删掉**第一条**销售流水时，第二条销售还在账上、狗确实已售，把状态改回在库是错的 |
| 关联到狗、是该狗最后一条销售流水，**但该狗已经是 `dead`** | **只删这一笔，不动状态**。这是可达路径：卖出去 → 退款把狗退回（`returned`）→ 又标了死亡（`dead`）。狗死了是**另一个事实**（无害化处理费已经按它记过、死亡率也把它算进去了），不能因为删掉一笔收入就把狗复活成在库 |
| 其他任何一笔（支出、注资、报销、分红、散收入） | 只删这一笔；**不改任何狗状态** |

池子余额、各人垫付、分账数字都是**从流水现算的派生值**，删除或修改后自动跟着变，不需要额外同步。不存在的 `id` → 返回**同一引用**（`actions.ts` 既有约定）。删除**没有撤销**，界面必须二次确认并写明连带动什么。

**两处要写进删除确认弹窗的提醒**（都是"账还能对上、但界面会对不上"的情况）：

- 删掉退款流水（`category: 'aftercare_refund'`）**不会**改狗状态，界面上的「已记退款」会消失、退款按钮重新出现——先确认那只狗到底退没退。
- 反过来，删掉**销售流水**会让狗回到在库，那笔残留的退款支出从此在界面上对不上任何一只狗（「钱」页不显示它挂在哪只狗上，见 4 的「钱」行）。确认弹窗里要把它挂的那只狗号写出来。
- 把一笔 `expense` 的 `category` 从 `aftercare_refund` 改掉，同样会让退款按钮重新出现、可能被**重复退一次款**。

> ✅ **复核结论（原文要求改动，复核后判定：不改）**：`src/ui/dogLedger.ts` 的 `lastSaleIndex` / `refundedCurrentSale` 用**数组下标**而不是 `date` 比较（`:35-36` 的注释写明「`entries` 是追加写的，下标顺序就是记账顺序」）。引入编辑与删除后这个前提**仍然成立**：`updateEntry` 只换字段、不重排数组；`deleteEntry` 是物理删除，删掉退款那笔后 `some(i > saleIdx)` 自然变 `false`。**改成按 `date` 找反而会坏**——`dogLedger.test.ts:62-68` 钉着「卖 → 退款 → 又卖出（同日）」，按日期找会命中那笔退款并返回 `true`，界面就只剩「已记退款」、用户再也点不到退款按钮。所以这一处**保持原样**，只由删除弹窗的文案兜住（见上）。

> 📌 **流水列表默认只显示最近 60 笔**（`MoneyPage.tsx:37` 的既有实现）。"每一笔都能改、能删"要成立，列表底部必须有「还有 N 笔更早的 · 显示全部」——点开后渲染全部倒序流水。不做分页（记几十笔是常态，全渲染没有性能问题），也不改这个默认值。

[]`。手机上已录入的数据必须照常打开，老备份文件必须照常能恢复，**新备份更要能原样还原（含预定单）**。

## 6. 测试策略

**算错钱是本项目唯一不可接受的失败。** 因此：

1. **单元测试（vitest）覆盖 `domain/` 全部纯函数**，重点用例：
   - 损耗摊薄：3.6 节的 8 只案例必须精确得出 973
   - 指标 A 与指标 B 在部分死亡、部分售出时各自的值
   - `aliveCount === 0` 不崩溃（整批死光）
   - `inStockCount === 0` 时不显示指标 A
   - 退狗（`returned`）：退款支出 + 回到在库，医疗成本不冲销
   - 垫付与报销的冲销
   - 五种流水对四本账的影响（逐条对照 3.3 的表）
   - 分账比例之和不为 1 时保存被拒绝
   - **检疫阶段推导**（3.7）：六个阶段各自一例，含"接种未满 `rabiesWaitDays` 天"与"证明刚好在有效期末尾"两个边界
   - **`isSellable` 铁律**：只有 `certified` 为 `true`；`cert_expired`、`waiting_cert`、`unvaccinated` 全部为 `false`
   - **出栏检查清单**：一批 8 只、其中 3 只无有效证明时，清单恰好列出那 3 只
   - **渠道对照**（3.8）：同一批狗在两条渠道下算出的保本单价不同；每条渠道的额外成本与固定成本都被计入；`undecided` 渠道不产生额外成本（等于 3.5 的基准值）
   - **渠道算法不重复**：渠道对照内部必须调用与 3.5 同一个"每只存活狗真实成本"函数，不允许另写一套
   - **预定单阶段推导**（3.9）：五个派生阶段各一例，含「正好提前 `preOrderLeadDays` 天」「就是今天」「晚一天算过期」三个边界；`received` 与 `cancelled` 优先于任何日期判定
   - **收货是一次原子操作**（3.9）：一次调用得到 1 个批次 + N 只狗 + **N 笔** `purchase` 流水 + 预定单 `status: 'received'`；**单价为 0 时一笔 `purchase` 都不写**（与 `planning.ts:116` 同口径，不写 0 元流水）；实收少于约定时只提示与留痕（差额写进批次 `note`，不改只数、不摊给别人）；实收 0 只或负数、`status` 不是 `reserved`、`id` 不存在，三种情况都必须返回**同一引用**
    - **预定单可改字段白名单**（3.9）：六个字段能改；`status` / `receivedCount` / `receivedBatchId` **无法**通过 `updatePreOrder` 改动（防绕过守卫收两次）；已收货的预定单只能改 `note`、不能删
    - **「算」页收货路径**（3.10）：`receiveBatch` 建出与 `receivePreOrder` 同样形状的批次与狗（走同一个 `addBatchWithDogs`），**除收购款外不写任何成本流水**；`count < 1` 返回同一引用
   - **补账表生成的笔数逐项对**（3.10）：`transport` 1 笔；`medical` 与 `quarantine` 按**这一批全部狗**数；`disposal` 只按**已标死亡**的狗数；**四行填 0 都不产生流水**；`previewBatchCosts` 报出的笔数与随后 `addBatchCosts` 实际新增的条数**必须相等**（两处口径只准有一份实现）
   - **补账"只新增不替换"（钉住语义）**：同一张表连点两次必须得到**两倍**流水（这是刻意行为，不是 bug）；`batchCostsIncomplete` 用「除 `purchase` 外有没有 `expense`」判定——**只记了收购款的批次必须为 `true`**，补过一笔后变 `false`
   - **流水纠错**（3.11）：改金额后保本价、盈亏、余额跟着变；金额沿用 `Math.max(0, Math.round())`（0 合法、负数被夹到 0，与新增路径同一口径）；**删掉该狗最后一条销售流水时，该狗必须在同一次更新里变回 `in_stock`**（返回新对象、原对象不被改；**但该狗当前已是 `dead` 时不动状态**——狗死了是另一个事实）；**删掉该狗更早的那条销售流水、而它还卖出过一次时，狗的状态一个字节都不许动**；删其他任何流水不改任何狗状态；不存在的 `id` 返回同一引用
   - **`refundedCurrentSale` 的追加顺序前提仍然成立**（3.11）：删掉退款流水后 `refundedCurrentSale` 必须变 `false`；「卖 → 退款 → 又卖出」这条既有回归（`dogLedger.test.ts`）必须继续通过——**这正是"这一处不需要改"的证据**
   - **老数据补齐（D16）**：`normalizeAppData` 对缺 `preOrders`、缺新设置项的旧对象补齐默认值；**导出 → 导入后 `preOrders` 逐条还原**（这一条专门用来钉住"白名单里写成 `[]`"那个错误写法）；导入旧格式备份后同样可用；已完整的数据语义不变
2. **手动验证清单**：真实手机浏览器上走一遍完整流程（**建预定单 → 到日子提醒 → 收货（只记收购款）→ 回批次补成本 → 记支出 → 卖出 → 死亡 → 改一笔流水 → 删一笔流水（含一笔销售流水，看狗是否回到在库）→ 出对账单 → 导出备份 → 用浏览器「清除站点数据」清空 → 导入恢复 → 确认含预定单在内的数据逐条还原 → 确认老数据未被破坏**）。清空**没有**界面按钮（见 1.3 非目标），手动验证时用开发者工具的 Application → Clear site data
3. **数据恢复演练**：备份文件必须能真正恢复，这是纸上谈兵最容易出错的地方

| **手机与电脑数据不一致** | 本地存储是"一台设备一份"，不会自动同步 | 约定以手机数据为准，电脑只用于存放备份文件 |

### 7.1 引流链路合规性（链路待定）

第一条硬事实：**抖音小店卖活狗这条路，门是关着的。**「宠物生活 / 宠物活体 / 狗活体」在行业规范里是**暂停招商**。

第二条硬事实：**「抖音发视频引流、加微信成交」是平台写明了要罚的做法**，不是灰色地带。禁止项明确包含微信号、二维码，以及「主页加微」「私信我」「看个性签名」这类变体，处罚上限是永久封禁账号。

**两条路同时堵着。这不是写软件能解决的问题，是商业决策。** 本工具能做、也已经做的只有三件事：

1. 把检疫与病死犬无害化处理两笔法定支出算进保本价（D9）；
2. 在设计文档里把这条链路标为「待定」，**不让第二期在一条不存在的路上修路标**；
3. 把两条路的合规原文与来源如实摆出来，交给你和合伙人判断。

**在链路确定为合规方案之前，「内容与流量归因」（第 9 节第 3 项）不得开工。**

> 一个必须说清的适用性细节：上述导流条款的主体表述是「**达人**在通过购物车分享商品的过程中」，最直接约束的是**开通了商品分享/带货功能的账号**；纯内容账号主要依《抖音社区自律公约》与《用户服务协议》处理。但这**不是安全区**——协议保留暂停/终止服务的权利，公约禁止大量重复发布无特定目标的内容，第三方观察也显示 2024–2025 抖音与小红书都在收紧私域导流。**别把「还没被封」当成「不违规」。**

## 8. 成功标准

1. 出门看狗之前，能在 30 秒内用"算"页面得出一个明确的收购价格上限

4. 录入一笔支出不超过 3 次点击

## 9. 第二期展望（不在本次实施范围）

> ⚠️ **第 3 项有前置条件，未满足前不得开工。** 它依赖一条合规的引流链路，而合规调研查明抖音明文禁止站外导流、狗活体类目又暂停招商（见 7.1）。链路确定之前做这个功能，等于给一条不存在的路修路标。

按真实发生顺序接入：

1. **客户线索跟进** —— 当咨询量起来后。设计方向：3 秒录入 + 到点提醒，而不是完整 CRM。**修订三的「预定单」（3.9）已经是线索的雏形**（卖家是谁 + 怎么联系 + 约了几只 + 约好哪天），届时应当把它升级为线索跟进，而不是另起一套并行的数据结构。
2. **售后退款 / 包赔** —— 当第一例索赔发生后，按真实流程设计
3. **内容与流量归因** —— **链路待定（见上方警告）**。确定合规链路后再设计：手工录入视频数据（播放/咨询数）与成交的关联
4. **云端同步** —— 若两人需要实时共享或数据丢失风险变得不可接受，替换 `storage/` 实现即可
5. ~~**检疫流程台账**~~ —— **已于修订二（D12）提前到第一期**，见 §3.7 与第 4 节「检」标签页。原因：无论走哪条销售渠道都必须有检疫证明，它不是"等货源模式变了再说"的功能。这是二期清单里唯一被提前的一项。

## 10. 待用户确认的开放问题

- 项目名称（暂用"狗账"）
- 两位合伙人的称呼与分成比例（默认各 50%）
- 成本项最终清单（当前为：收购价、运输 + 笼具、疫苗驱虫医疗、**检疫（抗体检测 + 申报）**、**病死犬无害化处理**；损耗自动计算）
- **各个渠道的实际成本**：犬市摊位费/进场费、宠物店的收购价水平、有没有走活体物流的渠道及单价（见 3.8 与 10.1 第 6 条）。渠道对照功能需要这些数字才不是空壳。
- **本地检疫的两个天数**：`rabiesWaitDays`（默认 21，**非法定值，见 §3.7**）与 `quarantineLeadDays`（默认 3，法定：《动物检疫管理办法》第八条第二款 +《犬产地检疫规程》4.1）在软件里是可改的设置项，等你打听到本地实际要求后填真值。
- **预定单提前几天提醒**：`preOrderLeadDays` 默认 **3 天**（§3.9），想提前一周就在设置里改数字。
- **预定单刻意不记的三样**（§3.9）：约定单价、定金、照片。将来要记再加——尤其"定金"要当成一种新的支出类型来考虑（钱出去了，但它是预付款、不是成本）。
- **补账表的两个口径**（§3.10）：疫苗与检疫按**这一批全部狗**算，处理费只按**已标死亡**的狗算。如果你们实际做法不同（例如疫苗只给活到出栏的狗打），告诉我：改的是一行代码，但历史账需要重算。
- **处理费是"点击那一刻"的快照**（§3.10）：补账时按当时已标「死亡」的只数生成流水；之后又死了一只，必须**再补一次**（表上填那一只的处理费）。**不自动追溯**——自动追溯就要反过来删掉/改掉已有流水，而"只新增不替换"是这一版的地基（D14）。这条如果你觉得太麻烦，可以改成"批次结算时一次算清"，但那要重新设计。
- **「钱」页只默认显示最近 60 笔**（§3.11）：底部有「显示全部」，不做分页。如果你觉得这个数字该改（比如 30 或 100），说一声就行，它只是 `MoneyPage.tsx:37` 里的一个字面量。
